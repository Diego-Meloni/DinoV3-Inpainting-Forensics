# Dinolizer: Inpainting Detection with DINOv3

## 1. Overview & Approach

The **Dinolizer** is an inpainting localization approach built on top of DINO foundation models (DINOv3 ViT, and DINOv3 ConvNext variants). It produces a dense per-pixel heatmap indicating the probability that each region of the image was generated by inpainting.

### Core Concepts

* **Backbone:** A frozen DINO model (ViT or ConvNext) acts as the feature extractor. The backbone is never fine-tuned; only a lightweight classification head is trained on top of its patch embeddings.
* **Patches:** The backbone divides the image into a grid of spatial tokens. For DINOv3 ViT this grid has an effective patch size of 16×16 pixels. For DINOv3 ConvNext models the effective patch size is 32×32 pixels due to the hierarchical downsampling of the CNN stages. This difference matters when choosing `--resize` or `--patch_based` sizes, since the resulting heatmap grid resolution scales accordingly (e.g. a 320×320 ViT input gives a 20×20 grid, while the same input on ConvNext gives a 10×10 grid).
* **Classification Head:** Several head variants are available — a simple linear head (`DinoLizer`), an MLP head (`DinoLizerMLP`), and a CNN head with spatial context (`DinoLizerCNN`). Equivalent ConvNext-backbone variants exist (`DinoLizerConvNext`, `DinoLizerConvNextCNN`). All heads project patch token embeddings to a per-patch logit, which is then upsampled to full image resolution.
* **Loss Function:** Two modes are available. The default is Dice loss only, matching the original DinoLizer paper baseline. Optionally, Focal + Dice loss can be combined (`--multi_loss`), with two ways of balancing the two terms (see Loss Configuration below).
* **Two Inference Modes:** Resize-based (image resized to a fixed square size, single forward pass) and patch-based (sliding window inference over the full-resolution image, results blended with Gaussian weighting). These are mutually exclusive and chosen via `--resize` / `--patch_based`.

## 2. Initial Setup

### Virtual Environment

We recommend using Python 3.10.20 to avoid library conflicts.

```bash
conda create -n dino_env python=3.10.20 -y
conda activate dino_env
python -m pip install -r requirements/requirements_dinolizer.txt
```

### Model Weights

Weights must be placed under `weights/`, in folders named after the model variant:

```
weights/
├── dinov3-vits/                  # DINOv3 ViT-Small/16
├── dinov3-convnext-tiny/         # DINOv3 ConvNext-Tiny
└── dinov3-convnext-small/        # DINOv3 ConvNext-Small
```

Each folder must contain the standard Hugging Face files (`config.json`, `model.safetensors` or `pytorch_model.bin`).

**Adding new model weights (e.g. DINOv2, larger backbones):** if you want to try a different backbone, place its weights in a similarly named folder under `weights/`. However, different backbones may output a different hidden dimension, a different effective patch size, or a different token layout (number of non-spatial tokens like cls/registers). Before using a new backbone with the existing model classes, inspect its output shape (see the `dinolizer_models.py` classes for the pattern used to adapt to DINOv3 ConvNext) and, if the patch size or token structure differs, create a new model class analogous to the existing ones (`DinoLizerConvNext` is a good template), adjusting the `grid_h, grid_w` calculation and the token-slicing logic to match the new backbone's structure.

## 3. Scripts Guide

### [1] Models & Utilities: `dinolizer/dinolizer_models.py`, `dinolizer/dinolizer_utils.py`

`dinolizer_models.py` contains:
- `DinoCSVDataset`: loads image/mask pairs from a CSV, applies transforms, optionally extracts balanced patches via `PatchGetter`.
- `JointTransform`: synchronized image/mask augmentation (resize, flips, rotation, color jitter, blur).
- `PatchGetter`: extracts and balances boundary/fully-inpainted/background patches for patch-based training.
- Model classes: `DinoLizer`, `DinoLizerMLP`, `DinoLizerCNN`, `DinoLizerConvNext`, `DinoLizerConvNextCNN`.

`dinolizer_utils.py` contains:
- `calculate_dice`, `compute_dice_loss`: metric and loss functions, shared identically between training and test.
- `extract_epoch_details`, `save_details_json`, `add_details_to_checkpoint`: checkpoint metadata management.
- `plot_visual_summary`: generates the test result visualization.

*Note: these files are not meant to be run directly. They are imported by the train and test scripts.*

### [2] Training: `dinolizer/1_dino_train.py`

Trains the classification head. Supports mixed precision, learning rate scheduling, early stopping, EMA or raw loss combination, and automatic checkpoint rotation (only best and latest epoch kept).

**Key arguments:**

| Argument | Description | Default |
|---|---|---|
| `--model_type` | Model class: `DinoLizer`, `DinoLizerMLP`, `DinoLizerCNN`, `DinoLizerConvNext`, `DinoLizerConvNextCNN` | required |
| `--model_dir` | Path to local DINO weights folder | `weights/dinov3-vits` |
| `--resize [SIZE]` | Resize-based training, optional size (default 320 if flag given alone) | `None` |
| `--patch_based [SIZE]` | Patch-based training, optional patch size (default 512). Must be divisible by 16 | `None` |
| `-e, --epochs` | Max number of epochs | 50 |
| `-bs, --batch_size` | Batch size | 16 |
| `-lr, --learning_rate` | Learning rate | 1e-4 |
| `-a, --augmentation` | Augmentation probability (0 disables augmentation) | 0.0 |
| `--multi_loss` | Use Focal + Dice instead of Dice only | off |
| `--normalize_loss` | EMA normalization for the two losses (only with `--multi_loss`) | off |
| `--alpha`, `--gamma` | Focal loss parameters | 0.6, 1.5 |
| `--retrain` | Delete existing checkpoints and start fresh | off |

`--resize` and `--patch_based` are mutually exclusive. If neither is specified, training defaults to `--resize 320`.

**Example commands:**

```bash
# Resize-based, Dice + Focal with EMA normalization
python 02_inpainting_detection/dinolizer/1_dino_train.py -e 20 -bs 16 -lr 1e-4 -a 0.3 \
  --multi_loss --normalize_loss --resize 320 \
  --dataset_dir dataset/SAGI-D --model_type DinoLizer --model_dir weights/dinov3-vits

# Patch-based training
python 02_inpainting_detection/dinolizer/1_dino_train.py -e 20 -bs 8 -lr 1e-4 -a 0.3 \
  --multi_loss --normalize_loss --patch_based 512 \
  --dataset_dir dataset/SAGI-D --model_type DinoLizer --model_dir weights/dinov3-vits

# Resize-based with ConvNext backbone (effective patch size 32, prefer larger resize)
python 02_inpainting_detection/dinolizer/1_dino_train.py -e 20 -bs 8 -lr 1e-4 -a 0.3 \
  --multi_loss --normalize_loss --resize 512 \
  --dataset_dir dataset/SAGI-D --model_type DinoLizerConvNext --model_dir weights/dinov3-convnext-tiny
```

### [3] Inference & Testing: `dinolizer/2_dino_test.py`

Evaluates a trained checkpoint on the test split. Training mode (resize vs patch-based) and model type are read automatically from the checkpoint, so they do not need to be re-specified.

**Key arguments:**

| Argument | Description | Default |
|---|---|---|
| `-w, --weights` | Path to checkpoint `.pth` file | required |
| `-d, --dataset_dir` | Dataset directory to test on | `dataset/flickr30k` |
| `-t, --threshold` | Binarization threshold | 0.5 |
| `-bs, --batch_size` | Batch size (forced to 1 if checkpoint is patch-based) | 16 |
| `-ts, --test_samples` | Number of random images shown in the summary plot | 5 |
| `--sw_size` | Override sliding window size (defaults to checkpoint's training patch size) | from checkpoint |
| `--model_type` | Override model class (defaults to checkpoint value) | from checkpoint |
| `--clean_test` | Delete previous Dinolizer test outputs before running | off |

**Example command:**

```bash
python 02_inpainting_detection/dinolizer/2_dino_test.py \
  -w models/checkpoints/dinolizer/dinolizer_best.pth \
  -d dataset/SAGI-D -ts 5 -t 0.5 --clean_test
```

Outputs are written to `predicted_masks/dinolizer/`: per-image heatmaps and binary masks, a `test_metrics_results.csv` with a metadata header, and a `summary_plot.png` visual report.

    ```bash
    python 02_inpainting_detection/dinolizer/comparison_generator.py -d dataset/SAGI-D --csv test/test.csv
    ```

#### `summary_plot_tester.py`
Generates a specific 4x4 image grid (saved as `thesis_plot_final.pdf`) intended for academic reporting and thesis formatting. It selects 4 hardcoded image basenames from the SAGI-D dataset and compares the Original, Ground Truth, Predicted Mask, and Predicted Heatmap. This guarantees a consistent 1:1 visual comparison across different model weights.
*   **Usage:** No arguments needed. Ensure the `target_basenames` list inside the script contains the exact images you want to evaluate before running.
*   **Command:**
    ```bash
    python 02_inpainting_detection/dinolizer/summary_plot_tester.py
    ```
*   **Output:** The PDF plot is saved in the same directory where the script is located.

## 4. Known Discrepancies Between Training, Validation, and Test

Across the three phases (training, validation, test) the metrics are not perfectly comparable, by design. This section explains why, so the numbers aren't misread as bugs.

### Training vs. Validation

Training accumulates loss once per batch and averages by number of batches. Validation accumulates loss once per image and averages by number of images. This is intentional given how each loop is structured (training always processes a full batch in one forward pass; validation iterates per-image to support both sliding window inference (when patch we have a patch-based training, this forces to batch size 1) and resize-based batched inference uniformly). The resulting scale of the two numbers is not directly comparable batch-for-batch, but each is internally consistent across epochs, which is what matters for monitoring training progress and triggering checkpointing.

Additionally, in `--multi_loss --normalize_loss` mode, the EMA normalization factors (`focal_running_mean`, `dice_running_mean`) are calibrated exclusively on training batches and held frozen during validation. Since training uses augmentation (random flips, rotation, color jitter, blur) and validation does not, the raw loss magnitudes differ between the two splits, and the frozen EMA factors amplify this into a small but consistent gap in the normalized combined loss. This is why `--normalize_loss` runs typically show validation loss a few hundredths higher than training loss, even with no overfitting. The raw Dice loss component (tracked separately) remains the reliable comparison point, which is why checkpointing is based on `val_dice_loss`, not the combined normalized loss.

### Validation vs. Test

Validation and test compute precision/recall/f1/iou identically (global TP/FP/FN accumulation, then ratios computed once at the end). The Dice score, however, is computed differently: validation averages a per-image Dice score across the validation set, while test computes a single global Dice score from the same accumulated TP/FP/FN used for the other metrics. Per-image averaging tends to be pulled down by images with small inpainted regions (where Dice is naturally noisier), while the global computation is dominated by the aggregate pixel counts. This structural difference explains part of why test Dice tends to read higher than validation Dice score for the same checkpoint.

In resize mode there is a second contributing factor: test upsamples predictions back to the original image resolution before computing metrics, while validation (for simplicity and speed) computes metrics directly at the resized resolution (e.g. 320×320). Upsampling via bilinear interpolation tends to smooth heatmap boundaries, which can marginally improve boundary-sensitive metrics like IOU and Dice at test time relative to validation.

### Practical takeaway

None of these differences indicate a computational bug — they reflect deliberate or structurally unavoidable differences in how each phase processes data. When comparing runs, always compare training-vs-training and validation-vs-validation across epochs (the trend, not the absolute cross-phase value), and treat the test metrics as the final, authoritative numbers since they are computed at full resolution with global aggregation, matching how the literature typically reports IOU/F1/Dice for image forgery localization.
